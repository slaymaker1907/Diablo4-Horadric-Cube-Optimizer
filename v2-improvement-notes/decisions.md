# Decisions

## Current Decisions

- The v3 implementation is being delivered in explicit phases from [original-plan.md](original-plan.md) rather than as a monolithic rewrite.
- The ILP solver is intentionally scoped to exact small binary ILPs. It is not a general branch-and-cut engine.
- The first runnable v3 slice implements feasibility checks and temporarily delegates feasible scenarios to the v2 exact solver.
- The Phase 3 ILP implementation uses presolve, two-phase simplex LP relaxations, most-fractional branching, and a rounded-LP repair heuristic; no cuts are implemented, so the solver must not be described as branch-and-cut.
- Continuous variables are supported only in the LP layer and direct tests; branch-and-bound decisions are currently binary-only because that is the only model family the worker plans to emit.
- The Phase 4 worker model consumes only decomposition-safe host options; unsupported or residual-only targets escalate into the Phase 5 residual solver instead of silently widening the decomposition assumptions.
- Multi-category targets are still decomposition-safe when the closed-form candidate fully specifies the action and prism choice (or deterministic enchant), so those options should be kept in the ILP layer instead of being pre-emptively escalated.
- Solver-limit behavior now prefers truthful approximate outputs over null-action failures when safe: decomposition may return a feasible ILP incumbent at `ITERATION_LIMIT`, and residual LAO* may return a best-so-far policy estimate with explicit approximate diagnostics.
- Approximation routing now uses a two-step rule: keep decomposition/ILP approximations by default for decomposition-safe cases, but when the ILP incumbent-vs-bound gap is wide, also solve residual and choose the final approximation by lexicographic objective with confidence tie-breaks.
- The current Phase 5 residual solver expands the abstract graph up front within a Thinking Time-derived budget (500-state / 4096-iteration base, up to 4096 states and 1048576 iterations with a steeper iteration ramp), then runs LAO*-style policy-graph backups on that abstraction. This keeps the implementation exact and testable for the supported residual slice while letting harder browser cases spend a larger exact budget.
- The public v3 worker contract always includes `diagnostics.feasibility`, `diagnostics.decomposition`, `diagnostics.ilp`, and `diagnostics.residual`; layers that do not run report explicit statuses such as `NOT_RUN` or `ESCALATED` instead of omitting fields.
- The Phase 8 contract review kept the current strategy IDs and status values unchanged; [d4cubeoptimv3.html](../d4cubeoptimv3.html) remains responsible for translating those stable internal labels into user-facing wording.
- Browser-worker imports share one global scope under `importScripts(...)`, so top-level bindings in [d4cubeoptimv3-worker.js](../d4cubeoptimv3-worker.js) must not reuse names already declared by imported worker scripts such as [d4cubeoptimv2-worker.js](../d4cubeoptimv2-worker.js).
- A decomposition ILP result of `INFEASIBLE` is treated as a routing miss, not a terminal user outcome; the worker escalates those cases into the residual solver because per-target decomposition options can still fail global host assignment even when the overall problem remains solvable.
- Repo-local markdown notes in `v2-improvement-notes` are mandatory artifacts and must be maintained throughout the project.
- The Rust MC verifier must recompute each rollout state's action via the **full** optimizer (ILP/decomposition first, then residual), exactly as JS does — never via a residual-only shortcut. A residual-only "policy table" fast-path was tried and removed: it bypassed the ILP/decomposition branch and therefore followed a different policy than the optimizer would, biasing MC step means even though pure `optimize` output stayed identical. Correctness of the MC mean takes priority over MC speed; per-state `action_cache` memoization (keyed by concrete `state_key`) is the only sanctioned MC speedup because it returns the optimizer's true action.
- Because the correct per-state MC is expensive on hard scenarios, **MC verification is off by default**: the "Result Verification" control defaults to `none`. Verification (Looser ≈100 rollouts / Tight adaptive) is strictly opt-in. The diff harness must guard the MC *mean* (not just action type + truncation rate) so a future policy/sampling regression that re-introduces bias cannot pass silently.
- Tier-1 Rust speedups must be **output-identical** and Rust-only (JS already memoizes these via `actionOutcomeCache` / `eligibleByCategoryCache` / `categoryWeightTotals*`). Three caches/optimizations are sanctioned: (1) per-`(slot,class,category,op)` affix-pool and `(family_counts,total_weight)` memoization on the env (pure function of those four keys, so memoizing is exact); (2) per-`(state_key,action_key)` MC outcome memoization; (3) residual-token outcome grouping in the BFS graph builder (`get_residual_action_outcomes_v3`). Grouping is correct because within a fixed placement context the residual child key is uniquely determined by the placed affix's residual token — the rest of the state is fixed, the family-uniqueness/no-duplicate filters are applied per affix before summing weights, the two compose renormalizations collapse into one over surviving outcomes, and the relevant-id ⊇ unsatisfactory-id invariant guarantees a trash placement never changes unsatisfactory counts (so one representative child per token group is exact). Validation gate: `expectedSteps` must stay byte-exact JS↔Rust on the benchmark scenarios and all diff-harness phases stay green.
