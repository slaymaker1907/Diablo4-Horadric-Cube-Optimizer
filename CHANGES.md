# CHANGES

## v2 to v3

This file tracks the staged transition from the v2 exact-SSP solver to the v3 hybrid architecture documented in [v2-improvement-notes/original-plan.md](v2-improvement-notes/original-plan.md).

## Current Status

- Phase 0 implemented: v3 worker scaffold, v3 HTML scaffold, ILP module scaffold, and repo-local handoff notes.
- Phase 1 implemented: feasibility checks F1 through F7 with structured diagnostics.
- Phase 2 implemented: closed-form Case A through G classification, exact expected-step formulas, residual-only explanations, and a stable target-slot coefficient table builder.
- Phase 3 implemented: exact small-problem ILP solving with presolve, two-phase simplex LP relaxations, most-fractional branch-and-bound, and a rounded-LP repair heuristic.
- Phase 4 implemented: the v3 worker now solves decomposition-safe cases end to end through the closed-form cost engine plus the scoped ILP layer.
- Phase 5 implemented: residual-only cases now route through an abstract-state residual solver with LAO*-style policy-graph backups and exact differentials against the abstract oracle.
- Phase 6 implemented: the v3 worker now exposes a stable top-level result contract across feasibility failure, decomposition success, residual success, and residual solver-limit outcomes, while preserving the existing done-message pattern.
- Phase 7 implemented: the v3 UI now renders the stable worker diagnostics contract, including feasibility failures, decomposition-versus-residual strategy choice, ILP outcomes, and residual solver-limit failures.
- Phase 8 implemented: requirement mapping, final validation consolidation, public-contract freeze review, and final handoff notes.

- **Fixed closed-form Case A enchant-follow-up under-cost (Bug 1)** and added a **stuck-recovery warning (Bug 2)**, plus a Monte Carlo correctness verification script. Bug 1: when no slot was currently enchanted, the optimal post-Add policy is `Enchant slot → target` (deterministic, 1 step), not retry-Add — but `computeCaseAExpectedStepsV3` was using the geometric formula `n - 1 + 1/n`, over-estimating headlines by ~2–5× (e.g. 6.14 reported vs MC's 1.86 for a simple 2-affix Add scenario). - Tightened the **"Expected Cube Steps" headline** by adding two layered improvements. **(1) Always-on one-step refinement (Approach 1):** when the residual LAO\* solver wins routing, `optimizePayloadV3` now performs a concrete one-step Bellman backup — for each `(p, successor)` outcome of the recommended action, it recursively calls `optimizePayloadV3(successor, { refineDepth: 0 })` and replaces the headline with `1 + Σ p_i × V(s'_i)`. Successors that route through the decomposition layer return exact values, so the headline tightens to essentially-exact in the common case (real example: 39.61 → 14.07 on a 4-affix Spiritborn Amulet residual case, perfectly matching `1 + E[post-Remove state]`). New `diagnostics.refinement` field records `{ applied, originalSteps, refinedSteps, outcomeCount }`. **(2) Opt-in gold-standard Monte Carlo verification:** a new "Tighten Steps Estimate" select in the toolbar Settings modal (with options None / Light / Heavy / Adaptive) runs MC rollouts with full re-optimization at every state, caching by state key. When enabled, the worker emits `type: "verifying"` progress messages and does NOT mark the run "Done" until MC completes — Optimize/Apply stay disabled, status shows "Verifying (k/K rollouts, n%)…". The headline updates from the Approach 1 value to the MC mean ± 95% CI when MC finishes. Adaptive mode stops when CI half-width ≤ 10% of mean (capped at 2000 rollouts / 120 s). Persisted to a separate `localStorage` key (`d4cubeoptim_tighten_v3`) that survives Reset. New diagnostics field `diagnostics.goldStandard` records `{ level, rollouts, mean, ci95halfWidth, stdev, truncatedRolloutCount, wallTimeMs, aborted, adaptive, earlyConverged }`. New constants: `MC_LIGHT_ROLLOUTS=100`, `MC_HEAVY_ROLLOUTS=500`, `MC_ADAPTIVE_MAX_ROLLOUTS=2000`, `MC_ADAPTIVE_WALL_BUDGET_MS=120000`, `MC_ROLLOUT_STEP_CAP=1000`. MC outcome sampling expands family-aggregate "Other" tokens (`elemental-damage-other`, `specific-resistance-other`) back to uniformly-random concrete family members, and filters outcomes that produce duplicate-affixId states (which the optimizer's downstream feasibility rejects), matching D4's in-game distribution. New benchmark script `scripts/benchmark-mc-rollouts.js` and opt-in slow regression script `scripts/expensive-mc-tests.js` (NOT run by default `node --test`). ## Planned Algorithmic Differences

- v3 will replace the monolithic exact-SSP approach with feasibility analysis, closed-form common-case costs, a scoped exact ILP for host assignment and ordering, and a residual LAO* solver.
- The ILP solver in [ilp.js](ilp.js) is intentionally scoped for exact small binary ILPs. It now implements presolve, two-phase simplex relaxations, and branch-and-bound without cuts, and it should not be described as branch-and-cut or state-of-the-art.
- The current residual implementation expands the abstract graph up front within a budget derived from Thinking Time (500-state / 4096-iteration base, up to 4096 states and 1048576 iterations with a steeper iteration ramp), then runs LAO*-style policy-graph backups on that abstraction. This is exact for the supported residual slice, but it is not yet a large-state sparse-expansion residual engine.
